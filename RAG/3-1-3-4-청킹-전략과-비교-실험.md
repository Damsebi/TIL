# 청킹 전략과 비교 실험

> 학습일: 2026-10-20

## 핵심 정리

- Chunking은 문서를 검색과 임베딩에 사용할 작은 단위로 나누는 과정이다. 크기뿐 아니라 문맥과 근거가 온전히 보존되는지도 중요하다.
- Chunk Size는 청크의 최대 크기이고 Overlap은 인접 청크가 공유하는 범위다. 정상적인 고정 길이 청킹의 이동 간격은 `size - overlap`이다.
- Overlap은 청크 경계의 문맥 손실을 완화하지만 중복 저장량, 반복 검색, Context의 토큰 사용량을 늘릴 수 있다.
- Fixed, Recursive, Token 청킹은 각각 문자 위치, 설정한 구분자, Tokenizer로 측정한 길이를 기준으로 문서를 나눈다.
- 청킹할 때 측정한 토큰 수와 최종 모델 입력의 토큰 수는 다를 수 있다. 접두사와 특수 토큰을 포함한 실제 입력을 확인해야 한다.
- Truncation은 초과한 내용을 제거하며, 잘린 부분을 다음 청크로 자동 보존하지 않는다.
- 구조 기반 청킹은 제목·절·표·목록의 관계를 고려한다. 원본 Metadata와 임베딩에 전달할 문자열도 구분한다.
- 근거 문장이 청크에 보존되는지와 실제 검색 결과에 필요한 청크가 포함되는지는 별도로 평가해야 한다.
- 청킹 설정이 바뀌면 변경된 청크에 맞춰 임베딩과 색인을 다시 구성하고, 기존 기준선과 구분해 관리한다.

## 1. Chunk Size와 Overlap

고정 길이 청킹은 일정한 크기로 문서를 자르고, 일부 구간을 겹치게 하면서 다음 청크로 이동한다.

```text
size = 80
overlap = 20
이동 간격 = 80 - 20 = 60

청크 1: [0:80]
청크 2: [60:140]
청크 3: [120:148]
```

이 예시의 단위는 문자다. Python의 `text[start:end]`는 `start`를 포함하고 `end`는 포함하지 않는다.

### Overlap은 크게 설정할수록 좋은가?

Overlap의 주요 목적은 청크 경계에서 문장이나 문맥이 끊기는 문제를 완화하는 것이다. 중요한 내용의 위치를 판단하는 기능은 아니다.

겹치는 구간이 많아지면 다음 비용도 증가한다.

- 같은 본문을 여러 청크에 중복 저장한다.
- 검색 결과에 비슷한 청크가 반복될 수 있다.
- Context에 같은 내용이 중복되어 토큰을 낭비할 수 있다.

따라서 문맥 보존 효과와 저장·검색 비용을 함께 비교해야 한다.

### Overlap이 Size 이상이면 어떻게 되는가?

교안의 `windows()`는 다음 반복문으로 시작 위치를 만든다.

```python
for start in range(0, len(text), size - overlap):
    end = min(start + size, len(text))
    result.append((start, end, text[start:end]))
```

입력 검증이 없는 상태에서 길이 148자의 문서에 적용하면 다음과 같다.

| Size | Overlap | 이동 간격 | `range()`의 결과 |
| --- | --- | --- | --- |
| 80 | 20 | 60 | 정방향 반복 |
| 80 | 80 | 0 | `ValueError` |
| 80 | 100 | -20 | `range(0, 148, -20)`은 빈 범위 |

`size=80`, `overlap=80`이면 같은 위치를 무한히 자르는 것이 아니라 `range()`가 간격 0을 허용하지 않아 오류가 발생한다.

`size=80`, `overlap=100`에서는 간격이 음수이지만 시작값 0에서 종료값 148로 이동할 값이 없다. 따라서 교안의 검증 없는 함수는 빈 목록을 반환한다.

```python
for start, end, piece in windows(text, 80, 100):
    print(f"[{start}:{end}]", piece)
```

직접 실습에서 출력이 없었던 이유도 바깥쪽 반복문이 빈 목록을 순회했기 때문이다. 여기서 `100`은 끝 위치가 아니라 세 번째 매개변수인 `overlap`이다.

실제 고정 길이 청킹에서는 다음 조건을 검사해야 한다.

```python
if not 0 <= overlap < size:
    raise ValueError("0 <= overlap < size")
```

오류 없이 실행되는 것과 올바른 청크가 만들어지는 것은 다르다.

### 역방향 청킹과 음수 이동 간격

Python의 `range()`는 음수 간격을 지원한다. 시작값이 종료값보다 크면 뒤에서 앞으로 반복할 수 있다.

```python
for i in range(10, 0, -2):
    print(i)
```

```text
10 → 8 → 6 → 4 → 2
```

문서 끝에서부터 청킹하려면 첫 끝 위치를 `size`가 아니라 전체 문서의 끝인 `len(text)`로 정한다.

```python
for end in range(len(text), 0, -(size - overlap)):
    start = max(0, end - size)
    result.append((start, end, text[start:end]))
```

80/20 설정과 문서 길이 148자를 적용하면 다음과 같다.

| end | end - size | 최종 start | 청크 |
| --- | --- | --- | --- |
| 148 | 68 | 68 | `[68:148]` |
| 88 | 8 | 8 | `[8:88]` |
| 28 | -52 | 0 | `[0:28]` |

`max(0, end - size)`는 시작 위치가 음수가 되지 않게 제한한다. 음수 인덱스를 그대로 사용하면 Python이 문서 끝을 기준으로 해석해 의도와 다른 구간을 참조할 수 있다.

정방향에서는 `min(start + size, len(text))`로 끝 위치를 제한한다.

`append()`가 튜플의 순서를 강제하는 것은 아니다. 교안에서 `(시작 위치, 끝 위치, 본문)`으로 정한 형식이며, 역방향 청킹에서도 각 청크의 시작 위치는 끝 위치보다 작게 유지한다. 결과 목록에 저장되는 청크의 순서만 뒤쪽부터 시작한다.

### 음수 간격과 실제 Overlap을 구분하기

`size=80`, `overlap=100`이면 `size - overlap` 자체가 -20이다. 이를 역방향 반복에 직접 사용하면 20자씩 이동할 수 있지만, 입력한 100이 실제 겹침 길이를 의미하지는 않는다.

직접 수정한 코드에서 확인한 앞의 두 청크는 다음과 같다.

```text
청크 1: [68:148]
청크 2: [48:128]

공유 구간: [68:128]
실제 겹침: 60자
```

80자짜리 청크가 20자씩 움직였으므로 실제 겹침은 `80 - 20 = 60`자다. 청크 크기가 80자인데 두 청크가 100자를 공유할 수는 없다.

실제로 100자를 겹치려면 크기를 그보다 크게 정해야 한다. 예를 들어 `size=120`, `overlap=100`이면 정상적인 이동 간격은 20자다.

유효한 Overlap 설정을 유지하면서 역방향으로 이동하려면 양수인 `size - overlap`에 방향을 나타내는 마이너스를 붙여 `-(size - overlap)`을 사용한다.

## 2. Fixed·Recursive·Token 청킹

| 방식 | 기준 | 확인할 점 |
| --- | --- | --- |
| Fixed | 문자 위치와 고정 길이 | 문장이나 조건이 경계에서 끊길 수 있다. |
| Recursive | 설정한 문단·문장·공백 등의 구분자 | 구분자를 고려해도 서로 다른 주제가 섞일 수 있다. |
| Token | Tokenizer가 계산한 토큰 길이 | 최종 입력의 접두사·특수 토큰까지 확인해야 한다. |

### Tokenizer만 불러오는 이유

```python
from transformers import AutoTokenizer

tokenizer = AutoTokenizer.from_pretrained(
    "intfloat/multilingual-e5-small"
)
```

- `AutoTokenizer`: 모델에 맞는 Tokenizer를 선택한다.
- `from_pretrained()`: Tokenizer 파일과 설정을 불러온다.
- `intfloat/multilingual-e5-small`: 사용할 모델 저장소 ID다.

이 단계는 임베딩 모델의 가중치를 불러오는 것이 아니다. 3-2강의 목적은 토큰 수 측정이므로 Tokenizer만 준비해도 된다.

실제 벡터를 생성하려면 임베딩 모델을 불러온다.

```python
from sentence_transformers import SentenceTransformer

model = SentenceTransformer(
    "intfloat/multilingual-e5-small"
)
vector = model.encode(
    "passage: " + text,
    normalize_embeddings=True,
)
```

교안에서 사용한 모델의 출력은 384차원이며 입력 한도는 최대 512토큰으로 정리했다.

| 기능 | Tokenizer만 로드 | 임베딩 모델 로드 |
| --- | --- | --- |
| 토큰 수 계산·토큰 ID 변환 | 가능 | 내부 Tokenizer로 가능 |
| 임베딩 벡터 생성 | 불가능 | 가능 |
| 모델 가중치 로딩 | 불필요 | 필요 |

`SentenceTransformer` 내부의 Tokenizer는 `model.tokenizer`로 사용할 수 있다.

### 청킹 토큰 수와 최종 입력 토큰 수

50토큰을 기준으로 청킹했더라도 최종 입력에는 접두사나 특수 토큰이 더해질 수 있다.

```python
token_count = len(
    tokenizer("passage: " + text)["input_ids"]
)

if token_count > 50:
    print("입력 한도 초과")
```

이 코드는 50토큰이라는 검사 기준의 초과 여부만 알려준다. 자동으로 재청킹하거나 잘리는 내용을 다음 청크로 보내지는 않는다.

51토큰이 나왔더라도 교안의 모델 한도인 512토큰을 넘긴 것은 아니다. 청킹을 위해 정한 목표 길이와 실제 모델의 입력 한도를 구분해야 한다.

### E5의 passage:와 query:

```python
text = "국내 출장 숙박 비용 한도는 1박당 12만원입니다."
input_text = "passage: " + text
```

| 접두사 | 용도 |
| --- | --- |
| `passage:` | 검색 대상 문서 |
| `query:` | 사용자 질문 |

E5 입력에는 이 접두사를 실제로 붙이므로 토큰 수를 확인할 때도 동일하게 포함한다. 모든 임베딩 모델이 같은 접두사를 사용하는 것은 아니다.

### Chunking과 Truncation의 차이

```python
tokenizer.truncation_side = "right"
tokens = tokenizer(
    "passage: " + text,
    max_length=50,
    truncation=True,
)
```

위 설정은 입력이 길면 뒤쪽 토큰을 제거해 최대 길이에 맞춘다. 토큰 수를 측정하기만 한다고 자동으로 이런 처리가 적용되는 것은 아니며, 실제 동작은 Tokenizer와 모델 호출의 설정에 따라 달라진다.

```text
Chunking
원본 100토큰
→ 앞부분 50토큰을 청크 1로 보존
→ 뒷부분 50토큰을 청크 2로 보존

Truncation
원본 100토큰
→ 앞부분 50토큰 유지
→ 초과한 뒷부분 50토큰 제거
```

Truncation은 잘린 내용을 다음 청크로 자동 이동시키지 않는다. 최종 입력 길이를 확인하고 초과한다면 사전에 청킹 설정을 조정해야 한다.

## 3. 한국어·문서 구조 기반 청킹

### 제목으로 먼저 나누는 이유

Recursive 청킹을 하더라도 교육비의 마지막 조건과 재택근무의 첫 조건이 같은 청크에 들어갈 수 있다. 제목으로 주제 범위를 먼저 나눈 뒤 각 절 안에서 크기를 조정하면 이런 혼합을 줄일 수 있다.

```text
원본 문서
→ 제목 기준으로 절 분리
   ├─ 교육비 지원
   └─ 재택근무 운영
→ 각 절 내부에서 Recursive 청킹
```

제목은 주제 경계를 정하고 Recursive 청킹은 그 안에서 크기를 조정한다. 절 제목인 `section`과 업무 분류인 `category`는 서로 다른 정보다.

### by_title과 원본 Metadata 연결

교안은 여러 문서를 하나의 Markdown 문자열로 합친 뒤 `MarkdownHeaderTextSplitter`로 나눈다. 여기서 `md`는 실제 파일일 필요 없이 Markdown 형식의 문자열일 수 있다.

```python
by_title = {
    d["metadata"]["title"]: d
    for d in chosen
}
```

일반 반복문으로 쓰면 다음과 같다.

```python
by_title = {}

for d in chosen:
    title = d["metadata"]["title"]
    by_title[title] = d
```

제목이 Key이고 원본 문서 전체가 Value다. 제목으로 절을 나누어도 원본 Metadata가 자동으로 연결되지는 않으므로 이 딕셔너리로 원본을 다시 찾는다.

```python
sections = header_splitter.split_text(md)

for sec in sections:
    orig = by_title[sec.metadata["section"]]
    sec.metadata.update(orig["metadata"])
    sec.metadata["document_id"] = orig["document_id"]
```

제목이 중복되면 딕셔너리의 이전 값이 덮어써져 다른 원본을 연결할 수 있다. 문서 ID로 구분하거나 처음부터 원본별로 처리하는 방식을 고려한다.

```python
sections = []

for d in chosen:
    md = f"## {d['metadata']['title']}\n{d['content']}"
    pieces = header_splitter.split_text(md)

    for sec in pieces:
        sec.metadata.update(d["metadata"])
        sec.metadata["document_id"] = d["document_id"]
        sections.append(sec)
```

원본별로 처리하면 현재 문서의 Metadata를 바로 전달할 수 있으므로 `by_title`이 필요하지 않다. 중첩된 Metadata를 청크별로 독립 수정해야 한다면 2장에서 다룬 깊은 복사도 함께 고려한다.

### Metadata와 임베딩 입력은 별개다

`model.encode(piece.page_content)`처럼 본문만 전달하면 Metadata에 저장된 제목은 임베딩에 자동으로 포함되지 않는다.

제목의 의미를 반영하려면 임베딩용 문자열을 별도로 구성한다.

```python
embedding_text = "\n".join([
    piece.metadata["title"],
    piece.page_content,
])

vector = model.encode("passage: " + embedding_text)
```

원본 본문과 Metadata는 유지하면서 임베딩에 전달할 문자열만 다르게 만드는 것이다.

`piece.metadata["title"] + "\n" + piece.page_content`로 연결해도 결과는 같다. `+`는 소수의 문자열을 직접 연결할 때, `join()`은 여러 문자열에 같은 구분자를 적용할 때 편하다.

제목을 추가하면 그 의미가 벡터 표현에 반영될 수 있다. Dense Retrieval은 제목의 특정 문자열이 포함되었는지만 검사하는 키워드 검색과 다르다.

### 표와 목록의 관계 보존

Overlap은 일정 범위를 기계적으로 겹치게 하지만 구조 기반 청킹은 정보 사이의 관계를 고려한다.

```text
항목    한도     주기
교육비  30만원   분기 1회
숙박비  12만원   1박당
```

표의 행을 분리할 때 열 이름을 함께 붙이면 값의 의미가 유지된다.

```python
headers = ["항목", "한도", "주기"]
rows = [
    ["교육비", "30만원", "분기 1회"],
    ["숙박비", "12만원", "1박당"],
]

chunks = []
for row in rows:
    fields = []
    for header, value in zip(headers, row):
        fields.append(f"{header}: {value}")
    chunks.append(" | ".join(fields))
```

```text
항목: 교육비 | 한도: 30만원 | 주기: 분기 1회
항목: 숙박비 | 한도: 12만원 | 주기: 1박당
```

이 예시는 각 행의 값 개수가 열 이름 개수와 같다는 전제다.

목록에서는 규정과 그 예외가 분리되지 않도록 묶을 수 있다.

```python
items = [
    "1. 숙박비는 1박당 12만원까지 지원한다.",
    "2. 단, 해외 출장에는 적용되지 않는다.",
    "3. 숙박 영수증을 제출해야 한다.",
]

chunks = []
for item in items:
    body = item.split(". ", 1)[1]
    if body.startswith("단,") and chunks:
        chunks[-1] += "\n" + item
    else:
        chunks.append(item)
```

`chunks[-1]`은 마지막으로 만든 청크다. 위 코드는 번호 목록에서 `"단,"`으로 시작하는 예외가 바로 앞 항목에 적용된다는 전제의 단순 예제다.

실제 문서에는 `"다만,"`, `"별도 규정을 따른다"`, `"제1항에도 불구하고"` 등 다양한 표현이 있으므로 하나의 규칙만으로 관계를 모두 처리하기 어렵다.

추가로 살펴본 대안은 규칙 확장, 제목·조항·번호 구조 활용, LLM의 관계 분석, 검색 후 인접 청크나 상위 조항을 함께 가져오는 방식이다. LLM도 적용 대상을 잘못 판단할 수 있으므로 원문 검증이 필요하다.

이 대안들은 보충 설명이며 교안에서는 관련 정보의 구조를 보존하는 원칙을 이해하는 수준으로 다뤘다.

## 4. 청킹 전략 비교와 선택

교안에서는 다음 세 근거가 한 청크 안에 온전히 보존되는지 비교했다.

1. 숙박비 1박당 12만원
2. 숙박 영수증 제출
3. 한도 초과 시 사전 서면 승인

아래 수치는 첨부한 교안의 실험 결과다.

| 설정 | 전체 청크 수 | travel 문서의 저장 문자 수 | 근거 보존 |
| --- | --- | --- | --- |
| 80/0 | 24 | 148 | 2/3 |
| 80/20 | 28 | 188 | 2/3 |
| 100/20 | 22 | 168 | 3/3 |

전체 청크 수는 전체 문서 기준이고 저장 문자 수는 travel 문서 기준이다. 저장 문자 수에는 Overlap으로 중복된 내용도 포함된다.

### 100/20에서 승인 조건이 보존되는 이유

승인 조건의 위치는 `[54:92]`다.

```text
80/20
[0:80]
[60:140]
[120:148]
→ 어느 청크에도 [54:92] 전체가 포함되지 않음

100/20
[0:100]
[80:148]
→ 첫 청크에 승인 조건 전체가 포함됨
```

80/20에서 Overlap을 사용했어도 모든 문장이 온전히 보존된 것은 아니다. 문장 위치와 길이에 따라 경계에 걸칠 수 있다.

### 더 잘 보존한 100/20 대신 80/20을 저장하는 이유

교안의 80/20은 최적 설정으로 확정된 값이 아니라 이후 임베딩·검색 실습에서 같은 데이터를 사용하기 위한 공통 기준선이다. 승인 조건이 끊기는 사례도 이후 검색·평가에서 다룰 문제로 남겨둔다.

실제 프로젝트에서는 100/20을 유력 후보로 선택해 평가할 수 있다. 공정한 비교를 위해 반드시 80/20을 사용해야 하는 것은 아니다.

- 임베딩 모델을 비교한다면 청킹 조건과 검색 조건을 고정한다.
- 청킹 전략을 비교한다면 임베딩 모델과 검색 조건을 고정한다.

핵심은 비교에서 바꿀 변수와 고정할 변수를 명확히 정하는 것이다.

### 근거 보존과 실제 검색 성능은 다르다

| 평가 항목 | 확인하는 내용 |
| --- | --- |
| 청크 수 | 검색 단위가 얼마나 생성되었는가 |
| 저장 문자 수 | 중복을 포함한 텍스트 양이 얼마나 되는가 |
| 근거 문장 보존 | 중요한 문장 전체가 한 청크에 들어가는가 |
| 실제 검색 성능 | 질문에 필요한 청크가 검색 결과에 포함되는가 |

교안에서 주로 확인한 것은 앞의 세 항목이다. 100/20이 세 근거를 보존했어도 실제 검색에서 해당 청크가 선택되는지는 검증하지 않았다.

반대로 80/20에서 문장이 나뉘었더라도 인접 청크가 함께 검색되면 필요한 정보를 확보할 가능성이 있다.

```text
청킹 설정 비교
→ 근거 보존과 저장량 확인
→ 유력 후보 선택
→ 설정별 청크를 각각 임베딩
→ 같은 질문·검색 조건으로 평가
→ 필요한 근거의 검색 여부와 비용 비교
→ 최종 설정 결정
```

이번 실험은 근거 보존의 차이를 확인하는 기초 실험이며, 모든 질문에 대한 최적 청킹 설정을 확정한 실험은 아니다.

## 5. 청크 저장과 후속 색인 관리

3-4강에서는 80/20 설정으로 12개 문서를 28개 청크로 나누어 `chunks.json`에 저장한다.

청크 ID는 다음 요소를 조합한다.

```text
문서 ID : 본문 해시 : Size : Overlap : 시작 위치
```

각 청크에는 원본 문서 ID, 본문, Metadata, 시작·끝 위치를 보관한다. 청킹 설정을 바꾸면 청크 ID와 본문 구간이 달라지므로 해당 결과에 맞는 임베딩과 색인을 다시 구성해야 한다.

대안 설정은 별도 파일로 관리해 기존 기준선과 섞이지 않게 한다.

### 식별·상태 필터·중복 판단의 차이

| 정보 | 역할 |
| --- | --- |
| `document_id` | 원본 문서 식별과 청크 추적 |
| `status` | 현행·구버전 구분과 검색 필터링 |
| `version`, `category`, 본문 해시 | 이전 교안의 문서 중복 판단 기준 |

교안의 중복 기준은 `(version, category, sha256(content))`였다. 문서 식별이나 현행 상태를 확인하는 것과 문서 중복을 판단하는 것은 구분한다.

## 오답 노트

| 처음 이해 | 수정된 이해 |
| --- | --- |
| Overlap은 인접 청크에 중요한 내용이 있을 가능성에 대비하는 기능이다. | 주요 목적은 경계에서 문장·문맥이 끊기는 문제를 완화하는 것이다. |
| Size와 Overlap이 같으면 같은 구간을 계속 슬라이싱한다. | 이동 간격이 0이 되어 Python의 `range()`에서 `ValueError`가 발생한다. |
| Overlap을 100으로 넣으면 실제로 100자가 겹친다. | 유효한 설정 범위를 벗어나면 입력값과 실제 겹침이 일치하지 않는다. 청크 크기와 이동 간격을 함께 확인한다. |
| 토큰 수를 출력하면 초과한 입력이 자동으로 처리된다. | 측정은 초과 여부만 알려준다. 재청킹이나 Truncation은 별도 처리다. |
| Truncation으로 잘린 내용은 다음 청크로 넘어간다. | 초과한 내용은 제거되며 자동으로 다음 청크에 보존되지 않는다. |
| Metadata에 제목이 있으면 자동으로 임베딩에 반영된다. | 모델에 전달하는 입력 문자열에 제목을 포함해야 한다. |
| 제목을 임베딩에 추가하는 것은 문자열 포함 여부로 검색하는 것이다. | Dense Retrieval에서는 제목의 의미도 벡터 표현에 반영될 수 있으며 키워드 검색과 다르다. |
| 100/20이 근거를 모두 보존했으므로 검색 성능도 더 좋다. | 근거 보존과 실제 검색 성능은 별도로 평가해야 한다. |
