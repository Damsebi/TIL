# 문서 로딩과 데이터 품질

> 학습일: 2026-10-19

## 핵심 정리

- TXT, HTML, PDF는 본문을 추출하는 방식이 다르며, 원본에 글자가 보인다고 추출된 텍스트도 정상이라는 뜻은 아니다.
- LangChain의 `Document`는 `page_content`에 본문을, `metadata`에 제목·상태·출처 등의 부가정보를 담는다.
- Metadata는 검색 필터링과 출처 추적에 사용하며, 문서 구조화 단계에서 기존 데이터나 규칙 등을 이용해 구성할 수 있다.
- 청크마다 중첩된 Metadata를 독립적으로 수정해야 한다면 `deepcopy()`로 참조 공유를 방지할 수 있다.
- SHA-256 본문 해시는 문서 내용의 변경 감지에 사용한다. 본문과 Metadata의 변경은 구분해야 한다.
- 공백·Boilerplate·중복·빈 본문을 정리하되 원문의 의미와 버전 정보를 보존하고 제외 사유를 기록한다.
- JSONL은 한 줄에 하나의 JSON 값을 저장하는 형식으로 순차 처리에 적합하지만, 처리 속도나 메모리 절약이 자동으로 보장되지는 않는다.
- `json.dumps()`와 `json.loads()`는 직렬화·역직렬화를 담당하며, JSON 문법과 데이터 구조·자료형은 별도로 검증한다.

## 1. 문서 로딩과 Document 구조

RAG에서 문서를 로딩한다는 것은 파일을 여는 것뿐 아니라, 검색에 사용할 본문을 추출하고 출처 정보와 함께 관리할 수 있는 형태로 만드는 과정이다.

```text
TXT / HTML / PDF
→ 형식에 맞는 본문 추출
→ 본문과 Metadata 구성
→ 정제·검수
→ 검색에 사용할 문서 저장
```

| 형식 | 확인할 부분 |
| --- | --- |
| TXT | 본문을 비교적 쉽게 읽을 수 있지만 공백과 빈 줄 등을 확인한다. |
| HTML | 태그와 본문 영역을 구분하고 메뉴·광고 등의 불필요한 영역을 제외한다. |
| PDF | 줄바꿈, 제목·꼬리말, 글꼴 인코딩, 텍스트 계층 유무를 확인한다. |

### Document는 무엇인가?

`Document`는 문서의 본문과 부가정보를 함께 관리하는 객체다.

```python
from langchain_core.documents import Document

doc = Document(
    page_content="출장 숙박비는 12만원입니다.",
    metadata={
        "title": "출장 숙박 정산",
        "status": "current",
    },
)
```

- `page_content`: 검색에 사용할 본문
- `metadata`: 제목, 상태, 출처 등 문서에 관한 정보

`Document` 객체 자체가 문서를 검색하거나 Metadata를 자동으로 생성하지는 않는다.

### 줄 정리 코드를 일반 반복문으로 풀어보기

```python
lines = [
    line.strip()
    for line in page_text.splitlines()
    if line.strip()
]
```

위 리스트 컴프리헨션은 다음과 같은 흐름이다.

```python
lines = []

for line in page_text.splitlines():
    if line.strip():
        lines.append(line.strip())
```

```text
splitlines()로 줄 단위 분리
→ 각 줄을 순회
→ strip() 후 내용이 있는지 검사
→ 양쪽 공백을 제거한 값을 리스트에 추가
```

리스트 컴프리헨션 맨 앞의 `line.strip()`은 결과 리스트에 넣을 값을 정한다. `if line.strip()`은 공백을 제거한 뒤 빈 문자열이 되는 줄을 제외한다.

### join()은 왜 구분자에서 호출하는가?

`join()`은 여러 문자열을 지정한 구분자로 연결하는 문자열 메서드다.

```python
words = ["사과", "바나나", "포도"]

" ".join(words)  # '사과 바나나 포도'
",".join(words)  # '사과,바나나,포도'
"".join(words)   # '사과바나나포도'
```

`text.split(" ")`에서 `text`는 나눌 대상이고, `" ".join(words)`에서 `" "`는 연결할 때 사용할 구분자다. 둘 다 `객체.메서드(인자)` 형태지만 메서드를 호출하는 객체의 역할이 다르다.

Python은 구분자 문자열에 `join()`을 정의해 리스트·튜플 등 다양한 문자열 이터러블을 연결하도록 설계했다. 메서드가 반드시 호출한 객체 자신만 처리해야 하는 것은 아니다.

## 2. 출처 추적을 위한 Metadata 설계

Metadata는 검색할 문서를 고르고 답변의 출처를 확인하는 데 사용한다.

| Field | 활용 |
| --- | --- |
| `status` | 현행·구버전 등 문서 상태를 기준으로 검색 필터링 |
| `category` | 주제나 문서 유형을 기준으로 검색 범위 제한 |
| `title` | 문서 식별과 출처 표시 |
| `version` | 적용 버전 구분과 변경 이력 추적 |
| `source_url` | 원본 위치 확인 |

### Metadata는 임베딩으로 자동 추출하는가?

Metadata를 구성하는 데 임베딩이 반드시 필요한 것은 아니다.

- 규칙 기반: 파일명, 날짜, 문서 구조 등에서 추출한다.
- 기존 데이터 활용: Database나 JSON에 이미 저장된 정보를 가져온다.
- LLM 활용: 문서 내용을 분석해 필요한 정보를 추출한다.

강의에서는 `documents.json`에 이미 존재하는 Metadata를 가져와 `Document`에 넣었다. 일반적인 벡터 검색 RAG에서는 문서를 구조화한 뒤 청킹과 임베딩을 수행한다.

### 얕은 복사와 깊은 복사

딕셔너리 안에 리스트나 다른 딕셔너리가 포함되어 있다면 바깥 객체와 내부 객체의 참조를 구분해야 한다.

| 방식 | 바깥 객체 | 내부 객체 |
| --- | --- | --- |
| `=` | 같은 객체를 참조 | 같은 객체를 참조 |
| `copy()` | 새 객체 생성 | 기존 내부 객체를 공유 |
| `deepcopy()` | 새 객체 생성 | 내부의 가변 객체도 재귀적으로 복사 |

얕은 복사는 바깥 객체만 새로 만든다. 내부에 있는 리스트나 딕셔너리를 수정하면 원본에도 영향을 줄 수 있다.

```python
from copy import deepcopy

metadata = {
    "title": "출장 숙박 정산",
    "tags": ["travel"],
}

shallow = metadata.copy()
deep = deepcopy(metadata)

shallow["tags"].append("policy")
# metadata["tags"]도 ["travel", "policy"]로 바뀐다.

deep["tags"].append("chunk")
# deep["tags"]는 ["travel", "chunk"]이며 원본은 바뀌지 않는다.
```

청크별로 Metadata를 깊은 복사하는 이유는 한 청크의 수정이 원본이나 다른 청크로 전파되지 않도록 하기 위해서다. 메모리 주소 자체를 복사한다고 이해하기보다 객체와 참조 관계를 구분하는 것이 핵심이다.

### 본문 해시로 변경 여부 확인

해시는 데이터의 길이가 아니라 내용을 바탕으로 계산한 고정 길이의 값이다.

| SHA-256 특징 | 의미 |
| --- | --- |
| 출력 크기 | 입력 크기와 관계없이 256비트 |
| 16진수 표현 | 64글자 |
| 내용 변경 | 일반적으로 해시값도 달라짐 |
| 원본 복원 | 해시값만으로 원본을 복원할 수 없음 |

```python
import hashlib

body_hash = hashlib.sha256(
    doc.page_content.encode("utf-8")
).hexdigest()

print(body_hash[:12])  # 표시용 축약값
```

이전 본문 해시와 현재 값을 비교하면 내용이 달라졌는지 확인할 수 있다. 다만 본문만 해시했다면 `status`나 `version` 같은 Metadata가 바뀌어도 본문 해시는 그대로일 수 있다.

### 해시 충돌은 왜 가능한가?

SHA-256의 출력은 $2^{256}$개로 제한되어 있지만 가능한 입력은 그보다 다양하므로, 서로 다른 입력이 같은 해시를 갖는 충돌이 이론적으로 존재한다.

실제로 SHA-256 충돌을 찾는 것은 매우 어려워 일반적인 문서 변경 감지에서 현실적인 문제는 드물다. 다만 앞 12글자만 비교하면 전체 해시보다 충돌 가능성이 높아진다. 강의의 `hash[:12]`는 축약 표시로 이해하고 전체 해시와 구분한다.

## 3. 중복·빈 본문·Boilerplate 정제

정제의 목적은 검색에 불필요한 데이터를 줄이면서 원문의 의미를 보존하는 것이다.

```text
추출한 본문
→ 공백 정규화
→ Boilerplate 제거
→ 빈 본문 확인
→ 중복 판별
→ 정제 결과와 제외 사유 기록
```

Boilerplate는 여러 문서에서 반복되는 메뉴, 안내문, 머리말·꼬리말 등 본문 검색에 불필요할 수 있는 내용이다. 반복된다는 이유만으로 중요한 적용 조건까지 제거하지 않도록 확인해야 한다.

강의에서는 `version`, `category`, 본문 해시를 조합해 중복을 판단했다. 본문이 비슷해도 버전이 다른 문서는 보존하고, 제외한 데이터와 제거 사유를 기록한다.

### 글자가 보이는데 텍스트가 추출되지 않을 수 있는가?

가능하다. 화면에 보이는 내용과 프로그램이 추출할 수 있는 텍스트는 다를 수 있다.

| 상황 | 발생할 수 있는 문제 |
| --- | --- |
| 텍스트 계층이 있는 PDF | `pypdf` 등으로 추출할 수 있지만 결과 확인이 필요함 |
| 이미지로만 된 스캔 PDF | 일반 텍스트 추출이 어려워 OCR이 필요할 수 있음 |
| HTML 본문 영역 선택 오류 | 원문에 내용이 있어도 빈 결과가 나올 수 있음 |
| PDF 글꼴 인코딩 문제 | 본문이 비어 있지 않아도 문자가 깨질 수 있음 |

따라서 빈 본문은 검색 대상에서 제외하더라도 원본에 내용이 없다고 단정하면 안 된다. 원본이 비어 있는 경우와 추출에 실패한 경우를 나누어 기록해야 한다.

빈 본문 검사만으로 모든 품질 문제를 찾을 수는 없다. 텍스트가 존재하더라도 잘못 추출되었는지 검수해야 한다.

### 사용자 질문에도 같은 정제를 적용해도 되는가?

공백이나 유니코드 표현을 정리하면 일부 검색 방식에서 도움이 될 수 있다. 다만 사용자 질문의 부정 표현, 코드, JSON 등의 구조를 바꾸면 의도가 훼손될 수 있다.

```text
원본 질문 보관
→ 검색용 질문을 별도로 전처리
→ Retriever 검색
→ 검색 결과와 원본 질문을 LLM에 전달
→ 답변 생성
```

문서와 질문 모두 필요한 범위만 정제하고 원래 의미를 유지해야 한다.

## 4. JSONL 저장과 데이터 검수

JSONL은 한 줄에 하나의 JSON 값을 저장하는 형식이다. 이 장의 문서 데이터는 각 줄에 본문과 Metadata를 가진 객체를 저장한다.

```jsonl
{"content": "출장 숙박비는 12만원입니다.", "metadata": {"status": "current"}}
{"content": "출장 식비 관련 규정입니다.", "metadata": {"status": "current"}}
```

이 예시에서 저장 필드인 `content`는 LangChain `Document`의 `page_content`에 대응한다. 저장할 때 정한 필드명과 다시 읽을 때의 변환 규칙을 일치시켜야 한다.

### 직렬화와 직렬 처리는 같은가?

서로 다른 개념이다.

- 직렬 처리: 작업을 순서대로 실행한다.
- 직렬화(Serialization): 데이터를 저장하거나 전송할 수 있는 형식으로 변환한다.

```text
Python dict
→ json.dumps()
→ JSON 문자열
→ json.loads()
→ Python dict
```

`json.dumps()`는 직렬화, `json.loads()`는 역직렬화에 해당한다.

### 본문에 줄바꿈이 있어도 한 줄로 저장되는가?

이스케이프는 특수한 의미를 가진 문자를 정해진 표기로 표현하는 것이다.

```python
import json

text = "안녕하세요\n반갑습니다"
packed = json.dumps({"content": text}, ensure_ascii=False)
restored = json.loads(packed)

assert restored["content"] == text
```

`json.dumps()`는 문자열 안의 실제 줄바꿈을 JSON의 `\n` 표기로 저장한다. 위 예시처럼 레코드 자체를 여러 줄로 꾸미지 않고 저장하면 본문의 줄바꿈 때문에 JSONL 레코드가 여러 줄로 나뉘지 않는다.

`json.loads()`로 읽으면 본문 안의 줄바꿈이 복원된다.

### JSONL을 한 줄씩 읽으면 더 빠른가?

JSONL은 무조건 빠른 형식이 아니라 순차 처리에 적합한 형식이다.

| 구분 | JSON 전체 배열 로딩 | JSONL 줄 단위 처리 |
| --- | --- | --- |
| 파싱 단위 | 전체 배열 | 레코드 한 줄 |
| 메모리 | 일반적인 전체 로딩에서는 전체 데이터를 보관 | 레코드를 처리하고 넘기면 필요한 데이터만 보관 가능 |
| 속도 | 데이터와 구현에 따라 달라짐 | 줄별 파싱 비용 때문에 더 느릴 수도 있음 |

강의의 `load_jsonl()`은 한 줄씩 읽더라도 모든 문서를 `result` 리스트에 저장했다. 따라서 최종 메모리 사용량은 전체 문서 크기에 비례한다.

줄 단위로 읽는 것과 전체 데이터를 메모리에 쌓지 않는 것은 다르다. JSONL의 장점을 활용하려면 이후 처리 방식도 함께 고려해야 한다.

### JSON 문법과 데이터 구조는 별도로 검증한다

`json.dumps()`를 정상적으로 사용하면 일반적으로 올바른 JSON을 만들 수 있다. 하지만 파일을 직접 수정하거나 저장이 중간에 끊기면 문법 오류가 발생할 수 있다.

또한 다음 데이터는 올바른 JSON이다.

```json
{"content": 12345}
```

하지만 본문을 문자열로 요구하는 RAG 처리에서는 잘못된 데이터다.

```text
JSON 문법 검사
→ 레코드가 기대한 객체인지 검사
→ 본문 필드가 문자열인지 검사
→ 빈 본문과 Metadata 등 필요한 조건 검사
```

문법적으로 읽을 수 있다는 사실과 다음 처리 단계에 적합한 데이터라는 사실은 다르다.

### enumerate()로 오류가 난 줄 번호 추적

`enumerate()`는 반복 대상의 값과 순서 번호를 함께 제공한다.

```python
fruits = ["사과", "바나나", "포도"]

for number, fruit in enumerate(fruits, 1):
    print(number, fruit)
```

```text
1 사과
2 바나나
3 포도
```

`enumerate(iterable, start=0)`에서 첫 번째 인자는 반복 대상이고 두 번째 인자는 번호의 시작값이다. 기본값은 `0`이다.

`enumerate(fruits, 1)`은 `(1, "사과")` 같은 튜플을 순서대로 제공한다. `for number, fruit`에서 튜플 언패킹으로 번호와 값을 각각 변수에 할당한다.

JSONL 검수에서는 `enumerate(stream, 1)`로 실제 파일 줄 번호에 맞춰 번호를 매기면 오류가 발생한 위치를 추적하기 쉽다.

## 오답 노트

| 처음 이해하거나 헷갈린 점 | 정리한 이해 |
| --- | --- |
| 해시는 데이터의 전체 길이를 나타낸다. | 데이터 내용으로 계산한 고정 길이의 값이다. SHA-256은 입력 크기와 관계없이 256비트를 출력한다. |
| Metadata는 임베딩으로 만들어야 한다. | 규칙, 기존 데이터, LLM 등으로 구성할 수 있으며 임베딩이 필수는 아니다. |
| 얕은 복사를 하면 내부 데이터도 독립적이다. | 중첩된 리스트·딕셔너리를 공유하므로 내부 수정이 원본에 영향을 줄 수 있다. |
| 빈 본문이면 원본 문서도 비어 있다. | 본문 추출에 실패했을 수 있으므로 원본 상태와 추출 결과를 구분한다. |
| JSONL을 줄 단위로 읽으면 메모리가 항상 적게 든다. | 읽은 결과를 모두 리스트에 저장하면 전체 문서 크기에 비례한 메모리가 필요하다. |
| 직렬화는 작업을 순서대로 처리한다는 뜻이다. | 직렬화는 데이터를 저장·전송 가능한 형식으로 변환하는 것이며 직렬 처리와 다르다. |
| JSON 파싱에 성공하면 본문도 올바른 데이터다. | JSON 문법과 객체 구조·본문 자료형·내용 품질은 별도로 확인해야 한다. |
