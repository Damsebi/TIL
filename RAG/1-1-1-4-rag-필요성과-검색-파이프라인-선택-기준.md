# RAG의 필요성과 검색 파이프라인·선택 기준

> 학습일: 2026-10-19

## 핵심 정리

- LLM은 Knowledge Cutoff, 비공개 데이터 접근, Hallucination 등의 한계가 있으므로 최신 정보나 사내 문서에 근거한 답변에는 외부 데이터 연결이 필요할 수 있다.
- RAG(Retrieval-Augmented Generation)는 관련 문서를 검색해 LLM에 근거로 제공하는 방식이며, 모델 가중치를 변경하지 않는다.
- Indexing은 문서를 미리 검색 가능한 형태로 준비하는 과정이고, Query는 준비된 색인에서 질문에 필요한 자료를 찾는 과정이다.
- Retriever는 문자열 검색, BM25, 임베딩 검색 등으로 구현할 수 있으며 반드시 머신러닝 모델일 필요는 없다.
- 2-Step RAG는 관련 자료를 찾는 Retrieval과 검색된 근거로 답변하는 Generation으로 구성된다.
- Chunk Size, Overlap, Top-k, Context 예산은 검색할 자료의 범위와 LLM에 전달할 근거를 결정한다.
- 현행 문서와 구버전을 구분하고, 검색 실패·근거 부족·답변 생성 오류를 각각 확인해야 한다.
- 출처 라벨이 유효하더라도 답변의 금액·단위·조건이 원문과 일치한다는 보장은 없다.
- RAG, Long Context, CAG, 실시간 API 조회는 자료의 양·변경 주기·반복 사용 여부·입력 예산을 기준으로 선택하며 실제 정확도와 처리 시간을 측정해야 한다.

## 1. RAG가 필요한 이유와 적용 조건

LLM이 학습한 지식만으로 모든 질문에 정확하게 답할 수는 없다.

| 한계 | 답변에 미치는 영향 |
| --- | --- |
| Knowledge Cutoff | 학습 이후에 바뀐 최신 정보를 반영하지 못할 수 있다. |
| Private Data | 학습에 포함되지 않은 사내 규정이나 비공개 문서를 알지 못할 수 있다. |
| Hallucination | 근거가 없거나 불충분해도 그럴듯한 내용을 생성할 수 있다. |

RAG는 질문에 관련된 외부 문서를 검색하고, 그 내용을 Context로 만들어 LLM에 전달한다.

```text
사용자 질문
→ Retriever 실행
→ 관련 문서 검색
→ 지시문·질문·검색 결과로 Prompt 구성
→ LLM
→ 근거를 참고한 답변 생성
```

이 과정에서 새로운 문서가 모델의 가중치에 학습되는 것은 아니다. 해당 요청의 입력에 참고 자료가 추가되는 것이다.

### 모든 질문에 RAG가 필요한가?

질문에 필요한 정보가 어디에 있고 어떻게 바뀌는지에 따라 접근 방법을 정한다.

| 상황 | 고려할 방식 | 이유 |
| --- | --- | --- |
| 여러 사내 규정에서 관련 조항을 찾아야 한다. | RAG | 질문과 관련된 문서를 먼저 선택해야 한다. |
| 개인별 실시간 배송 상태를 확인해야 한다. | API 조회 | 최신 상태를 해당 시스템에서 직접 가져와야 한다. |
| 사용자가 이미 분석할 문서를 제공했다. | 문서 직접 입력 | 필요한 자료가 이미 입력에 있다. |

자료를 검색할 필요가 있는지, 실시간 조회가 필요한지, 이미 제공된 자료로 충분한지를 먼저 판단한다.

## 2. Retriever와 LLM의 역할

기본적인 RAG에서는 프로그램이 Retriever를 실행한 뒤 검색 결과를 LLM에 전달한다. LLM이 직접 모든 문서를 검색하는 것은 아니다.

```text
Retriever
→ 질문에 필요한 문서나 청크 선택

Context 구성
→ 선택한 근거를 LLM 입력으로 정리

LLM
→ 질문과 Context를 참고해 답변 생성
```

Retriever는 반드시 머신러닝 모델일 필요가 없다. 단순 문자열 검색, BM25 같은 단어 기반 검색, 임베딩 기반 검색 등으로 구현할 수 있다.

### 검색어는 코드에 직접 작성해야 하는가?

강의의 기초 구현은 문서에 검색어가 포함되어 있는지 확인했다.

```python
found = [d for d in current if term in d["content"]]
```

`term`은 사용자 입력에 따라 동적으로 전달할 수 있다. 검색어를 하드코딩해야 하는 것은 아니다.

다만 이 구현은 문자열이 그대로 포함되는지를 검사한다. `"숙박 비용"`이 있는 문서를 찾더라도 같은 의미의 `"호텔비"`로는 검색하지 못할 수 있다.

임베딩 검색은 질문과 문서를 벡터로 표현해 의미적 유사성을 비교할 수 있지만, 관련 문서를 항상 정확하게 찾는 것은 아니다.

### 리스트 컴프리헨션의 `d for d`는 어떻게 작동하는가?

위 코드를 일반 반복문으로 바꾸면 다음과 같다.

```python
found = []

for d in current:
    if term in d["content"]:
        found.append(d)
```

- `for d in current`: 문서를 하나씩 순회한다.
- `if term in d["content"]`: 본문에 검색어가 포함되어 있는지 검사한다.
- 앞의 `d`: 조건을 만족한 문서를 결과 리스트에 넣는 표현식이다.

앞의 `d`에 값을 저장하는 것이 아니라 조건을 만족한 문서를 `found`에 추가하는 구조다.

## 3. Indexing과 Query 파이프라인

Indexing은 질문이 들어오기 전에 문서를 검색 가능한 형태로 준비하는 과정이다. Query는 준비된 색인을 이용해 실제 질문에 필요한 자료를 찾는 과정이다.

```text
[Indexing]
원본 문서
→ 문서 처리·청킹
→ 검색용 색인 생성

[Query]
사용자 질문
→ 색인 조회
→ 관련 문서·청크 선택
→ 원본 내용 조회
```

### 색인과 역색인은 어떤 관계인가?

Index는 검색에 사용하는 자료 구조를 통틀어 부르는 개념이다. Inverted Index(역색인)는 그중 `단어 → 문서 ID` 관계를 저장하는 방식이다.

```text
문서 중심 구조
문서 A → 사랑, 행복
문서 B → 사랑, 우정

역색인 구조
사랑 → {A, B}
행복 → {A}
우정 → {B}
```

역색인은 검색 행위 자체가 아니라 검색에 사용하는 자료 구조다. 색인과 역색인은 반대 개념이 아니라 상위 개념과 구체적인 구현 방식의 관계다.

### 역색인과 원본 문서의 관계

강의에서는 역색인에 문서 전체가 아닌 문서 ID를 저장하고, `by_id` 같은 구조로 원본 문서를 조회했다.

```text
"사랑" 검색
→ 역색인에서 {A, B} 확인
→ by_id로 A, B의 원본 조회
→ 문서 본문 반환
```

실제 검색 엔진은 문서 ID 외에 단어 빈도나 등장 위치 등을 저장할 수도 있다.

### OR 검색과 AND 검색

```text
사랑 → {A, B}
행복 → {A}

사랑 OR 행복
→ 합집합 {A, B}

사랑 AND 행복
→ 교집합 {A}
```

단순 역색인은 단어의 의미나 조사 차이를 이해하지 못한다. 관련 문서 ID를 찾는 것과 관련성 순위를 계산하는 것도 별개의 작업이다.

### 문서가 바뀌면 색인도 갱신해야 하는가?

문서가 추가·수정·삭제되면 색인에도 변경 사항을 반영해야 한다.

| 방식 | 처리 |
| --- | --- |
| 전체 재색인 | 모든 문서를 다시 처리해 색인을 재생성한다. |
| 증분 색인 | 추가·수정·삭제된 문서의 변경 사항만 반영한다. |

증분 색인에서는 새 문서의 단어를 추가하고, 수정된 문서의 기존 색인 정보를 갱신하며, 삭제된 문서가 검색되지 않도록 제거하거나 삭제 상태를 반영한다.

구버전을 반드시 물리적으로 삭제할 필요는 없다. `metadata.status`를 `retired`로 보관하고 현재 규정을 묻는 검색에서는 `current` 문서만 선택할 수도 있다. 실제 검색 엔진은 삭제 표시나 지연된 정리 방식을 사용할 수 있다.

## 4. 2-Step RAG 기준선

2-Step RAG는 Retrieval과 Generation을 순서대로 수행하는 구조다. 강의의 함수 이름으로 표현한 흐름은 다음과 같다.

```text
read_documents
→ chunk_documents
→ retrieve
→ build_context
→ generate_ollama
```

문서를 읽고 청크로 나눈 뒤 관련 청크를 검색하고, Context를 구성해 LLM 답변을 생성한다. 이를 기준선으로 두면 이후 검색 방식이나 청킹 전략을 바꿨을 때 결과를 비교할 수 있다.

### Chunk Size와 Overlap

Chunking은 문서를 검색 가능한 작은 단위로 나누는 과정이다. 강의의 `80/20` 예시는 다음 의미다.

```text
Chunk Size 80
→ 청크 하나를 최대 80자로 구성

Overlap 20
→ 인접한 청크 사이에 20자를 겹치게 구성
```

이 숫자는 고정 규칙이 아니다. 단위도 이 실습에서는 문자 기준이며, 다른 구현에서는 토큰 등 다른 단위를 사용할 수 있다.

고정 길이 청킹은 문장의 의미를 판단하지 않고 나누므로 중요한 문장이 경계에서 끊길 수 있다. Overlap은 일부 내용을 중복해 포함함으로써 문맥 단절을 완화한다.

청킹은 일반적으로 Indexing 단계에서 수행한다. 질문이 들어온 뒤 Retriever는 미리 만들어진 청크에서 관련 자료를 검색한다.

강의에서는 고정 길이 청킹을 사용했다. 질문을 통해 추가로 확인한 방식에는 문장·문단·문서 구조 기준의 분할과, 임베딩 등으로 주제가 바뀌는 지점을 찾는 의미 기반 청킹이 있다.

### BM25와 Top-k

BM25는 단어 빈도, 단어의 희소성, 문서 길이 등을 고려해 청크의 관련성 점수를 계산한다.

Top-k는 검색 결과로 선택할 청크의 최대 개수다. 검색된 청크가 모두 LLM 입력에 포함되는 것은 아니다.

```text
BM25로 관련성 점수 계산
→ 상위 k개 청크 선택
→ Context 예산에 맞게 포함할 청크 결정
→ 선택된 근거를 LLM에 전달
```

Context에 사용할 수 있는 입력 예산이 작다면 Top-k로 검색한 청크 중 일부가 제외될 수 있다.

## 5. Context와 출처 라벨

Context에는 검색된 근거를 정리하고, 지시문과 질문을 함께 넣어 Prompt를 구성한다. 답변에는 금액뿐 아니라 단위, 적용 대상, 적용 조건도 정확하게 반영해야 한다.

### S1, S2는 실제 문서 이름인가?

`S1`, `S2`는 이번 Context에 포함한 근거에 순서대로 붙이는 임시 출처 라벨이다.

```text
[S1] 출장 숙박 정산
국내 출장 숙박 비용 한도는 1박당 12만원입니다.

[S2] 출장 식비 정산
출장 식비 관련 규정...
```

```text
답변: "1박당 12만원입니다. [S1]"
→ 이번 요청의 S1 출처 조회
→ document_id: travel
→ 원본 문서와 해당 청크 확인
```

- `travel`: 원본 문서의 식별자
- `S1`: 이번 Context에서 첫 번째로 포함된 근거의 식별자

따라서 `S1`이 항상 `travel`을 뜻하지는 않는다. 하나의 원본 문서에서 여러 청크가 포함되었다면 서로 다른 라벨이 같은 문서를 가리킬 수도 있다.

검색되었더라도 Context 예산 때문에 제외된 청크에는 출처 라벨을 부여하지 않는다.

## 6. 검색과 답변 검증을 나누어 보기

RAG의 실패는 어느 단계에서 문제가 생겼는지 구분해야 원인을 찾을 수 있다.

| 구분 | 예시 | 확인할 부분 |
| --- | --- | --- |
| 검색 실패 | 필요한 문서가 있어도 검색하지 못함 | 검색어, 색인, Retriever, 필터 |
| 답변 근거 부족 | 검색된 자료만으로 질문의 조건을 판단할 수 없음 | Context의 범위와 정보 충족 여부 |
| 문서 선택 오류 | 구버전을 현행 규정으로 선택함 | 문서 상태, 적용 시점, 적용 대상 |
| 답변 생성 오류 | 올바른 근거를 주었지만 금액이나 조건을 잘못 답함 | 답변과 원문 내용의 일치 여부 |

### 출처 검증을 통과하면 내용도 정확한가?

다음 답변은 출처 형식과 라벨의 존재 여부 검사에는 통과할 수 있다.

```text
원문: 숙박비 한도는 12만원입니다.
답변: 숙박비 한도는 15만원입니다. [S1]
```

`S1`이 실제 Context에 있다는 사실과 답변 내용이 해당 근거에 부합한다는 사실은 다르다.

```text
JSON 형식이 올바름
≠ 출처 라벨이 유효함
≠ 답변 내용이 근거와 일치함
```

강의에서 실습한 검증 범위는 JSON 형식과 출처 라벨까지다. 답변 내용의 자동 검증과 개선은 질문을 통해 추가로 공부한 내용이다.

내용 오류를 검출할 수 있다면 재생성 후 재검증하거나 답변을 보류할 수 있다. 오류 기록을 모아 검색, Context 구성, Prompt를 개선하고 성능을 다시 평가하는 데 활용할 수도 있다.

검증 데이터를 누적한다고 LLM 가중치가 자동으로 바뀌지는 않는다. 재생성은 현재 답변을 다시 만드는 작업이고, 파인튜닝은 별도 학습으로 가중치를 변경하는 작업이다.

### 상반된 문서가 함께 검색되면 어떻게 되는가?

```text
문서 A: 출장 숙박비는 8만원까지 지원한다.
문서 B: 출장 숙박비는 12만원까지 지원한다.
```

두 문서는 주제가 같으므로 함께 검색될 수 있다. 적용 시점이나 유효성을 구분하지 못하면 구버전을 선택하거나, 서로 다른 문서의 조건을 섞거나, 근거에 없는 금액을 만들 수 있다.

구버전인 8만원을 선택하는 것은 문서 선택 오류로 볼 수 있고, 두 금액을 섞어 근거에 없는 10만원을 만드는 것은 명확한 Hallucination 사례다. 규정의 충돌을 설명하고 답변을 보류하는 대응도 가능하다.

Retriever가 올바른 문서를 찾았더라도 LLM이 내용을 잘못 해석할 수 있으므로 검색 정확도와 답변 정확도를 함께 관리해야 한다.

## 7. RAG·Long Context·CAG 선택 기준

세 방식은 서로 다른 역할을 하며 함께 사용할 수도 있다.

| 구분 | 핵심 역할 | 살펴볼 조건 |
| --- | --- | --- |
| RAG | 질문과 관련된 자료를 검색해 전달 | 전체 자료의 양, 검색 품질, 문서 변경 주기 |
| Long Context | 긴 입력을 처리하는 모델의 능력 | 입력 예산, 긴 자료를 실제로 활용하는 정확도 |
| CAG | 공통 입력의 계산 상태를 캐싱해 재사용 | 공통 자료의 반복 사용, 캐시 지원, 갱신 정책 |

Long Context는 검색을 대체하는 별도 검색기가 아니다. RAG로 검색한 여러 자료를 긴 Context로 전달하는 방식처럼 함께 사용할 수 있다.

### 문서에 사용할 수 있는 입력 예산

Context Window 전체를 문서에 사용할 수는 없다. 지시문, 대화 이력, 질문, 출력에 예약할 공간 등을 함께 고려해야 한다.

```text
모델의 Context Window
− 지시문
− 대화 이력
− 사용자 질문
− 출력 예약 공간과 기타 입력
= 문서에 사용할 수 있는 예산
```

문서가 이 예산을 초과한다면 RAG로 관련 자료를 고르거나 전달할 범위를 줄여야 한다. 예산 안에 들어가더라도 실제로 중요한 정보를 잘 활용하는지는 확인해야 한다.

### CAG는 언제 적합한가?

이 장에서 다룬 CAG(Cache-Augmented Generation)는 공통 자료를 처리한 계산 상태, 예를 들어 KV Cache를 저장하고 반복 요청에서 재사용하는 접근이다.

```text
공통 사내 규정
→ LLM이 공통 입력 처리
→ KV Cache 저장
→ 직원 A 질문에서 재사용
→ 직원 B 질문에서 재사용
```

질문 형식이 일정한지보다 참고하는 공통 자료를 반복해서 사용하는지가 중요하다. 자료가 입력 예산 안에 들어가고 변경이 적으며 실행 환경이 캐시를 지원한다면 전체 자료 입력과 Prefix Cache의 효과를 비교할 수 있다.

캐시는 원본 문서 파일을 보관하는 것과 다르다. 문서를 처리하면서 계산한 상태를 재사용하므로 문서가 변경되면 관련 캐시도 갱신하거나 무효화해야 한다.

캐시 키는 모델, 입력 내용, 문서 범위 등을 구분하는 식별자다. 키를 생성했다고 실제 KV Cache가 저장되거나 재사용되는 것은 아니다.

### API 라우팅이나 결과 캐싱도 CAG인가?

재사용하는 대상이 다르다.

| 구분 | 재사용하는 대상 |
| --- | --- |
| CAG | LLM이 공통 입력을 처리한 계산 상태 |
| 라우팅 | 질문 유형에 따라 작업이나 API를 선택하는 규칙 |
| API 결과 캐싱 | 이전 API 조회 결과 |

```text
사용자 질문
→ 질문 유형 분류
→ 배송 문의를 배송 조회 API로 연결
→ 실시간 배송 상태 조회
→ 답변 생성
```

반복적인 API 선택을 규칙으로 처리하면 불필요한 LLM 호출을 줄일 수 있다. 이는 처리 경로를 최적화하는 방법이며 CAG와 구분한다.

API 결과를 캐싱한다면 최신성을 고려한 유효시간과 갱신 정책이 필요하다. 최종 방식은 실제 데이터로 정확도와 처리 시간을 측정해 결정한다.

## 8. 추가로 이해한 내용: 벡터 연산과 의미적 정확성

### LLM은 많은 문서를 어떻게 처리하는가?

```text
입력 문서
→ Tokenization
→ 토큰 임베딩
→ Transformer의 문맥 처리
→ 다음 토큰 확률 계산
→ 답변 생성
```

Attention은 토큰 사이의 관계를 계산하고 GPU는 대규모 행렬 연산을 병렬로 처리할 수 있다. 다만 긴 입력을 처리할 수 있다는 사실이 모든 정보를 정확하게 활용한다는 뜻은 아니다.

### 토큰 임베딩과 문장 임베딩의 차이

- 토큰 임베딩은 학습된 임베딩 테이블에서 토큰 ID에 대응하는 벡터를 조회한다.
- 문장 임베딩은 학습된 신경망 연산으로 문맥을 반영한 벡터를 계산한다.

두 과정 모두 입력마다 모델을 새로 학습시키는 것은 아니다. RAG의 임베딩 기반 검색에서는 문서 벡터를 미리 계산해 저장하고 질문 시점에는 질문 벡터와 비교할 수 있다.

```text
[Indexing]
문서 → 임베딩 모델 → 문서 벡터 저장

[Query]
질문 → 임베딩 모델 → 질문 벡터
→ 저장된 문서 벡터와 비교
→ 관련 문서 검색
```

이 벡터 검색과 LLM 내부의 문맥 처리는 서로 다른 과정이다.

### 수치 계산이 정상이어도 왜 답변이 틀릴 수 있는가?

```text
A: 회사는 숙박비를 지원합니다.
B: 회사는 숙박비를 지원하지 않습니다.
```

두 문장은 단어와 주제를 많이 공유하므로 임베딩 공간에서 가까울 수 있지만, 부정 표현 때문에 실제 의미는 반대다.

벡터 유사도는 관련성을 나타낼 수 있어도 같은 사실을 말한다는 점이나 어느 문장이 참인지를 보장하지 않는다. LLM 역시 정상적으로 연산하더라도 모든 정보를 올바르게 선택하고 해석한다는 보장은 없다.
