# 데이터 수집과 API·RAG 기초

> 학습일: 2026-09-21

## 핵심 정리

- 데이터를 찾을 때는 값이 자주 바뀌는지, 앞뒤 맥락이 필요한지, 과거 데이터와 비교해야 하는지를 먼저 고려한다.
- 국내 공공 데이터는 공공데이터포털, AI 학습용 데이터는 AI Hub 같은 플랫폼에서 찾을 수 있으며 외부 서비스가 제공하는 API를 통해 가져올 수도 있다.
- CSV는 표 형태의 데이터, JSON은 중첩 구조나 API 응답처럼 구조가 복잡한 데이터에 적합하다.
- 웹페이지의 데이터는 HTML에서 직접 추출하거나 개발자 도구의 Network 탭에서 페이지가 호출하는 API를 확인해 수집할 수 있다.
- RAG에서는 근거 문장만 저장하기보다 답변에 필요한 앞뒤 문맥까지 하나의 Chunk에 포함하는 것이 좋다.
- 수정되거나 삭제될 수 있는 외부 데이터는 특정 시점의 원본을 Snapshot으로 저장하고, 이를 가공해 Chunk·Embedding·Vector DB를 갱신할 수 있다.
- 외부 데이터 수집, RAG, LLM은 서로 다른 역할을 한다. 수집기가 데이터를 확보하고, RAG가 관련 정보를 검색하며, LLM은 검색 결과를 바탕으로 답변한다.
- 수집 전에는 License, 이용약관, 접근 권한, 자동 수집 허용 여부, 개인정보 처리 조건을 확인하고 목적에 필요한 Field만 수집한다.

## 1. 필요한 데이터와 접근 가능성 판단

데이터 수집을 시작하기 전에는 먼저 어떤 정보가 필요한지 정해야 한다.

```text
수집 목적 정의
→ 필요한 데이터와 Field 결정
→ 데이터 변경 주기 확인
→ 앞뒤 문맥의 필요성 확인
→ 과거 데이터와의 비교 필요성 확인
→ 실제 접근 가능 여부 확인
```

데이터가 자주 바뀐다면 주기적인 갱신이나 실시간 조회가 필요할 수 있다. 문장 하나만으로 의미를 이해하기 어렵다면 주변 문맥도 함께 저장해야 한다. 시간에 따른 변화를 비교해야 한다면 현재 값만 덮어쓰지 않고 날짜별 원본을 남겨야 한다.

### 데이터는 어디에서 찾을 수 있는가?

국내 공공 데이터는 공공데이터포털에서, AI 학습용 데이터는 AI Hub와 같은 플랫폼에서 찾을 수 있다. 기업이나 다른 서비스가 제공하는 외부 API를 이용하거나 웹페이지에서 직접 수집할 수도 있다.

AI Hub는 민간 서비스가 아니라 공공 AI 지원 플랫폼이다. 외부 서비스 API는 특정 기업이나 서비스의 데이터 또는 기능을 프로그램에서 Request하여 사용하는 방식이다.

### 데이터가 존재하면 항상 사용할 수 있는가?

데이터의 존재와 실제 접근 가능 여부는 다르다. API가 있어도 인증키나 권한이 필요할 수 있고, 시스템에 연결되지 않았거나 웹 접근이 차단되어 있으면 원본을 가져올 수 없다.

```text
데이터 존재
→ 접근 방법 확인
→ 인증·권한·연결 상태 확인
→ 실제 데이터 수집
→ 검증된 데이터만 사용
```

접근하지 못한 정보는 확인된 사실처럼 다루면 안 된다.

## 2. API와 Web을 통한 데이터 수집

### 외부 API로 데이터 가져오기

외부 API를 이용하면 정해진 Endpoint에 Request를 보내고 JSON 등의 Response를 받을 수 있다. 이때 우리 프로그램은 데이터를 제공하는 Server가 아니라 외부 API를 사용하는 Client 역할을 한다.

```text
우리 프로그램
→ 외부 API에 Request
→ Response 수신
→ 필요한 데이터 정제·저장
```

### F12로 크롤링한다는 것은 무엇인가?

`F12` 자체가 데이터를 크롤링하는 것은 아니다. 브라우저 개발자 도구의 Elements에서 HTML 구조를 확인하고, `Network → Fetch/XHR`에서 웹페이지가 내부적으로 호출하는 API를 찾을 수 있다.

페이지가 JSON API를 호출하고 있다면 HTML을 직접 Parsing하는 것보다 해당 API의 Response를 이용하는 편이 더 간단할 수 있다. 다만 내부 API가 보인다는 사실만으로 자동 수집과 재사용까지 허용된다는 뜻은 아니다.

## 3. CSV와 JSON 선택

| 형식 | 적합한 데이터 | 특징 |
| --- | --- | --- |
| CSV | 행과 열로 구성된 단순한 표 | Excel이나 pandas에서 다루기 쉽다. |
| JSON | 중첩된 객체·목록, API 응답 | 복잡한 계층 구조를 표현하기 좋다. |

```text
CSV
→ 표 형태 데이터

JSON
→ 구조가 복잡한 데이터
→ API Response
```

형식은 익숙함보다 데이터 구조와 이후 처리 목적을 기준으로 선택한다.

## 4. Snapshot과 데이터 갱신

외부 데이터는 시간이 지나면서 수정되거나 삭제될 수 있다. 특정 시점의 원본을 Snapshot으로 남겨두면 과거 데이터와 현재 데이터를 비교하고, 당시 답변에 사용한 근거를 추적하거나 가공 과정을 다시 실행할 수 있다.

```text
외부 데이터 수집
→ 날짜별 원본 Snapshot 저장
→ 정제
→ Chunk 분할
→ Embedding
→ Vector DB 저장
```

Snapshot 원본은 일반적으로 File System이나 Object Storage 등에 보관하고, 검색에 사용하는 Embedding은 Vector DB에 별도로 저장한다.

원본과 가공 결과를 분리하면 Chunk 기준이나 Embedding Model이 바뀌어도 원본을 다시 수집하지 않고 재처리할 수 있다.

## 5. RAG의 데이터 처리와 질문 흐름

### 왜 앞뒤 문맥까지 저장하는가?

근거 문장 하나만 저장하면 문장 속 지시어가 무엇을 가리키는지, 어떤 조건에서 성립하는지 알기 어려울 수 있다. 검색된 내용만으로 의미를 이해할 수 있도록 근거 문장과 필요한 주변 문맥을 하나의 Chunk에 포함하는 것이 좋다.

Chunk가 너무 짧으면 문맥이 끊길 수 있고, 너무 길면 관련 없는 내용까지 함께 검색될 수 있다. 따라서 문서의 구조와 질문 유형에 맞게 범위를 정해야 한다.

### 데이터는 사용자가 질문할 때 저장되는가?

일반적인 RAG에서는 질문을 받을 때마다 처음부터 데이터를 수집하지 않는다. 데이터를 미리 수집하고 검색 가능한 형태로 가공한 뒤 주기적으로 갱신한다.

```text
[사전 작업]
데이터 수집
→ 원본 저장
→ 정제
→ Chunk 분할
→ Embedding
→ Vector DB

[질문 시점]
사용자 질문
→ 관련 Chunk 검색
→ LLM에 검색 결과 전달
→ 답변
```

실시간성이 매우 중요한 데이터는 질문 시점에 외부 API를 직접 호출하는 방식으로 구성할 수도 있다.

### 모델이 계속 실행되면서 데이터를 수집하는가?

LLM 자체가 계속 실행되며 데이터를 모으는 것은 아니다. 별도의 Crawler 또는 API 수집 프로그램을 만들고 Scheduler로 정해진 주기에 실행한다.

```text
Crawler / API 수집기
→ 데이터 저장 및 갱신

사용자 질문
→ RAG 검색
→ LLM
→ 답변
```

### RAG 없이도 수집한 데이터로 답변할 수 있는가?

가능하다. 질문이 들어온 시점에 Crawler나 API를 호출해 최신 데이터를 확보하고 바로 LLM에 전달할 수 있다.

```text
[실시간 조회]
사용자 질문
→ Crawling / API 호출
→ 최신 데이터 확보
→ LLM
→ 답변
```

반면 RAG는 미리 저장하고 색인한 데이터에서 질문과 관련된 내용을 검색한다.

```text
[RAG]
데이터 수집·저장
→ Vector DB 구성

사용자 질문
→ 관련 데이터 검색
→ LLM
→ 답변
```

외부 데이터를 수집할지는 RAG 사용 여부가 아니라 외부 정보가 필요한지를 기준으로 판단한다.

## 6. 데이터 수집 전 리스크 점검

웹에 공개된 데이터라고 해서 수집·가공·재사용이 모두 허용되는 것은 아니다. 수집 전에 다음 항목을 확인한다.

- 데이터 License와 재사용 조건
- 이용약관과 운영정책
- API·개발자 정책
- 자동 수집 허용 여부
- 로그인, 인증키, 접근 권한
- 개인정보와 민감정보 포함 여부
- 수집 목적과 필요한 Field의 범위

### 약관이나 License를 찾기 어렵다면 어떻게 하는가?

이용약관, 개인정보처리방침, API·개발자 정책, `robots.txt`, 데이터 License를 확인하고도 불명확하면 공식 담당 부서에 문의한다.

법무팀, 데이터 담당팀, 개발자 지원팀, 운영팀 등 답변 권한이 있는 부서에 수집 목적·방법·범위·이용 목적을 구체적으로 적어 문의하는 것이 좋다. Email처럼 기록이 남는 답변은 이후 판단 근거로 활용할 수 있다.

답변이 없거나 조건을 확인하지 못했다면 허용된 것으로 간주하지 않고 `허용 여부 불명확` 상태로 남겨둔다.

### `robots.txt`가 있으면 Crawling이 차단되는가?

`robots.txt`는 Crawler에게 특정 경로의 수집 허용 여부를 알리는 안내 규칙이다. 요청을 기술적으로 차단하는 보안 기능은 아니다.

```text
robots.txt
→ Crawler에게 수집 규칙 안내

로그인 / 권한 인증 / 403 / IP 차단
CAPTCHA / Rate Limit / WAF·Bot 탐지
→ 실제 요청 제한 또는 차단
```

`robots.txt`에서 허용된 경로라도 이용약관이나 License가 재사용까지 허용한다는 뜻은 아니므로 각각 확인해야 한다.

### 필요한 Field만 수집해야 하는 이유

데이터는 가능한 한 많이 모으는 것이 아니라 수집 목적에 필요한 범위만 선택한다.

```text
수집 목적 정의
→ 목적 달성에 필요한 Field 판단
→ 불필요한 Field 제거
→ 필요한 데이터만 수집
```

예를 들어 상품 리뷰 감성 분석이 목적이라면 리뷰 내용과 평점은 필요할 수 있지만 전화번호나 주소처럼 분석과 관계없는 개인정보까지 수집할 필요는 없다.

### 해외 공공 데이터는 자유롭게 사용할 수 있는가?

국가나 공공기관이 공개한 데이터라도 모두 국가 소유이거나 자유롭게 이용 가능한 것은 아니다. 중국을 포함한 해외 공공 데이터도 플랫폼별 이용약관, 회원가입 조건, License, 재사용 범위, 개인정보·중요 데이터 여부를 각각 확인해야 한다.

일부 공개 데이터에 해외에서도 접근할 수 있다는 사실을 모든 데이터가 제한 없이 사용 가능하다는 의미로 일반화하면 안 된다.

## 오답 노트

| 처음 이해 | 수정된 이해 |
| --- | --- |
| `robots.txt`가 Crawling Request를 직접 차단한다. | `robots.txt`는 수집 규칙을 안내한다. 실제 차단은 인증, `403`, IP 차단, CAPTCHA, Rate Limit, WAF 등의 Server 장치가 수행한다. |
| 외부 데이터가 존재하면 LLM이 바로 사용할 수 있다. | 데이터가 있어도 인증·권한·연결이 없으면 접근할 수 없다. 실제로 수집해 LLM에 전달하는 과정이 필요하다. |
| LLM이 계속 실행되며 최신 데이터를 수집한다. | 별도의 Crawler나 API 수집기가 데이터를 확보하고, RAG가 검색하며, LLM이 검색 결과를 이용해 답변한다. |
| RAG를 사용해야만 Crawling 데이터를 답변에 쓸 수 있다. | 실시간 Crawling/API 조회 결과를 바로 LLM에 전달할 수도 있다. RAG는 미리 저장·색인한 데이터의 검색에 적합하다. |
