# 커밋 메시지 작성 가이드

커밋 메시지만 보고도 어떤 변경이 이루어졌는지 알 수 있도록 일관된 형식으로 작성한다.

## 기본 형식

```text
타입: 변경 내용 요약
```

예시:

```text
docs: README 목차 추가
```

## 커밋 타입

| 타입 | 의미 | 예시 |
| --- | --- | --- |
| `feat` | 새로운 기능 추가 | `feat: 로그인 버튼 추가` |
| `fix` | 버그 수정 | `fix: 플레이어 이동 오류 수정` |
| `docs` | 문서 추가 또는 수정 | `docs: README 내용 보완` |
| `refactor` | 기능 변화 없이 코드 구조 개선 | `refactor: 입력 처리 로직 분리` |
| `chore` | 빌드, 설정, 패키지 및 기타 작업 | `chore: gitignore 설정 추가` |
| `test` | 테스트 코드 추가 또는 수정 | `test: 플레이어 이동 테스트 추가` |

## 작성 규칙

- 하나의 커밋에는 하나의 목적만 포함한다.
- 변경 내용을 짧고 명확하게 작성한다.
- 커밋 메시지만 보고도 어떤 작업인지 알 수 있도록 작성한다.
- `수정`, `작업`, `최종`처럼 범위가 불분명한 표현만 사용하지 않는다.
- 한글과 영어 중 하나를 정해 저장소 전체에서 일관되게 사용한다.

## 좋은 예시

```text
feat: 플레이어 이동 기능 추가
fix: 체력 UI 갱신 오류 수정
docs: Git 기본 명령어 문서 추가
refactor: 입력 처리 메서드 분리
chore: gitignore 설정 추가
test: 플레이어 이동 로직 테스트 추가
```

## 피하는 것이 좋은 예시

```text
수정
작업함
여러 가지 변경
최종 수정
진짜 최종
```

## TIL 저장소에서 자주 사용할 예시

새로운 학습 문서를 추가한 경우:

```text
docs: Git 개념 학습 문서 추가
```

기존 문서의 설명을 보완한 경우:

```text
docs: Git 학습 문서 내용 보완
```

README 목차와 링크를 수정한 경우:

```text
docs: README 학습 목차 정리
```

여러 Markdown 문서를 함께 정리한 경우:

```text
docs: Git TIL 문서 내용 정리
```

## 정리

좋은 커밋 메시지는 변경의 목적을 짧고 명확하게 전달하며, 나중에 커밋 기록을 확인할 때 작업 내용을 쉽게 파악할 수 있도록 도와준다.
